# Snaply 기획 재정의 — AI 숏폼 브이로그 제작 앱

작성일: 2026-07-28 · 상태: **제안 (미확정)**

이 문서와 옆의 프로토타입 3종은 아직 확정 기획이 아니다. 방향이 정해지면 그때
`docs/features/*`와 코드에 반영한다 (프로젝트 규칙상 기능 문서는 구현과 같은 작업에서 갱신).

| 파일 | 방향 | 홈이 무엇인가 |
| --- | --- | --- |
| [`p1-daily.html`](p1-daily.html) | **오늘 — AI 제안형** | AI가 찾아낸 “만들 거리”의 큐 |
| [`p2-studio.html`](p2-studio.html) | **스튜디오 — 작업대형** | 담아둔 재료 + 진행 중인 작업 보드 |
| [`p3-recipe.html`](p3-recipe.html) | **레시피 — 의도 우선형** | 만들 수 있는 결과물의 카탈로그 |

브라우저로 파일을 열면 왼쪽에 방향 설명, 오른쪽에 클릭 가능한 목업이 뜬다. 3개는 서로
코드를 공유하지 않는 독립 파일이다.

## 1. 무엇이 문제였나

현재 기획은 “필름을 찍고 → 하루가 끝나면 현상한다”는 은유 위에 서 있다. 이 은유가
제품 규칙까지 지배하면서 다음 제약을 만들어냈다.

- **하루 1롤 강제** — 여러 날에 걸친 영상, 주제별 영상을 만들 수 없다.
- **미현상 블러** — 사용자가 자기가 방금 찍은 영상을 못 본다. 은유를 위해 기능을 뺐다.
- **지연 현상** — 만들고 싶을 때 못 만든다. 하루가 끝나야 한다.
- **AI가 안 보인다** — “현상”이라는 의식(ceremony) 뒤에 숨어서, 이게 AI 제품인지 필름
  감성 아카이브 앱인지 구분되지 않는다.

원래 의도는 **AI 기반 숏폼 브이로그 제작 앱**이었다. 은유가 그 의도를 덮었다.

### 버리는 것

`하루 1롤` · `현상(develop) 의식` · `미현상 블러(negative frame)` · `필름 그레인·퍼포레이션·
edge print` · `12컷 목표` · `보관함(archive)이라는 탭 이름` · `지오펜스 기반 자동 수집`

### 남기는 것

3–5초 짧은 촬영 · 원본은 불변, 조합은 별도(N:M) · 다크 팔레트 · 촬영 리마인더 ·
푸시/위치 알림 인프라 · 인증/설정 전반

> 다크 팔레트는 남긴다. 영상 앱에 어두운 배경은 은유가 아니라 기능이다. 다만 앰버
> safelight·필름 질감 같은 “필름임을 주장하는” 장식은 뺀다. 프로토타입 3종은 같은
> 팔레트를 쓴다 — 비교 대상이 색이 아니라 **구조**여야 하므로.

## 2. 제품 한 줄 정의

> **짧게 여러 번 찍어두면, AI가 한 편의 숏폼 브이로그로 만들어 주는 앱.**

두 개의 명사만 있으면 제품이 설명된다: **재료**와 **완성작**.

## 3. 용어와 탭 이름

| 개념 | 제안 이름 | 이유 / 대안 |
| --- | --- | --- |
| 3–5초 원본 조각 | **스냅** (Snap) | 브랜드명 Snaply와 직결. 그대로 유지 권장. |
| AI가 합성한 결과물 | **무비** (Movie) | “스냅↔무비 = 재료↔완성작” 대비가 즉시 읽히고, 단위로도 자연스럽다(“무비 3편”). 대안: `릴`(인스타 릴스와 충돌), `브이로그`(장르명이라 단위로 어색), `에피소드`(연재물 느낌), `컷`(스냅과 혼동). |
| 프로필 + 설정 | **나** | 한 글자. `마이`, `프로필`보다 짧고 한국어 앱 관례에 맞다. |
| 홈 | 방향마다 다름 | 홈의 이름은 홈이 담는 것에서 나온다 — `오늘` / `스튜디오` / `레시피`. |
| 촬영 | 탭바 중앙 ● 버튼 | 탭이 아니라 액션. 4탭 + 중앙 버튼 = 5슬롯(틱톡/인스타 관례). 어느 탭에서든 촬영 가능. |

**“폼”은 쓰지 않기를 권한다.** 어원(필름)이 버릴 컨셉에 묶여 있고, 한국어에서 “폼”은
form(양식)으로 먼저 읽힌다.

## 4. 정보 구조 (3종 공통)

```text
탭바:  [홈] [스냅] (●촬영) [무비] [나]

스냅 탭   내가 찍은 3–5초 원본. 날짜별 그리드. 즉시 재생 가능(블러 없음).
          우상단 [선택] → 다중 선택(최대 10) → 무비로.
무비 탭   완성작 + 초안. 2열 그리드. 열면 재생 / 컷 수정 / 스타일 변경 / 재생성 / 공유.
          우상단 [+] → 스냅 선택 모드로 진입.
나  탭    프로필 · 통계 · 리마인더 · 알림 · 연결된 계정 · 계정 관리 (기존 설정 그대로).
홈  탭    ← 여기가 세 방향의 유일한 차이점.
```

무비를 만드는 경로는 항상 **두 개**다. (사용자 요구사항 그대로)

1. 스냅 탭에서 다중 선택(≤10) → 바로 무비 만들기
2. 무비 탭 / 홈에서 “새로 만들기” → 스냅 선택 → 만들기

## 5. 데이터 모델과 기존 코드 매핑

핵심: **모델은 거의 그대로 쓸 수 있다.** 바꿀 것은 이름과 규칙이지 구조가 아니다.

| 지금 | 바뀔 것 | 비고 |
| --- | --- | --- |
| `entities/clip` · `Clip` | `entities/snap` · `Snap` | 필드 거의 동일. `mood`는 재검토(캡처 옵션 대신 무비 스타일로 이동). |
| `entities/roll` · `Roll` + `Reel` | `entities/movie` · `Movie` | 롤과 릴을 하나로 합친다. 릴은 “developed된 롤”이 아니라 무비의 렌더 산출물. |
| `ClipRef { clipId, order, trim }` | `SnapRef` 그대로 | N:M + per-무비 순서/트림 구조는 그대로 유효하고 좋다. |
| `RollStatus: undeveloped / developing / developed` | `MovieStatus: draft / generating / ready / failed` | `failed` 추가 필수 — AI 잡은 실패한다. |
| `RollType`, `CollectionRule`, `DailyRollTarget(12)`, `rollDate` | 삭제 | 하루 1롤·자동 수집 규칙을 버리므로 전부 불필요. |
| — | `Movie.style`, `Movie.bgm`, `Movie.jobId`, `Movie.renderedUri` | 신규. |
| — | `snapRefs.length <= 10` | 유일한 하드 제약. |

영향 범위 (참고용, 확정 후 정리):

- `features/`: `collect-clips` + `develop-roll` → `compose-movie` 로 통합. `capture-moment`는 유지.
- `widgets/`: `roll-shelf`(월별 현상 선반), `clip-membership`(역인덱스) → 무비 목록 요구사항에
  맞춰 재검토. 대부분 단순해진다.
- `pages/`: `home` · `archive` · `roll-detail` · `cut-strip` → `home` · `snaps` · `movies` ·
  `movie-detail` 로 재편.
- `shared/ui/`: `negative-frame`(블러 미현상), `film-grain` → 제거 대상.
- `docs/features/`: 전 문서 재작성 대상.

## 6. 프로토타입 3종 비교

|  | **P1 오늘 (제안형)** | **P2 스튜디오 (작업대형)** | **P3 레시피 (의도 우선형)** |
| --- | --- | --- | --- |
| 홈에 있는 것 | AI가 묶은 제안 카드 스택 | 담기 트레이 + 진행 중 보드 | 프롬프트 + 레시피 카탈로그 |
| 첫 무비까지 탭 수 | **2회** | 6–8회 | 3–4회 |
| AI의 역할 | 기획자 (뭘 만들지 정해줌) | 도구 (마지막에 붙음) | 캐스팅 디렉터 (틀에 맞춰 채움) |
| 사용자 통제감 | 낮음 | **높음** | 중간 |
| 콜드 스타트 (스냅 0개) | 취약 — 홈이 빈다 | 보통 — 할 일은 안내됨 | **강함** — 뭘 찍을지 보인다 |
| 촬영 유도 | 약함 | 약함 | **강함** — 빈 슬롯이 촬영을 지시 |
| 백엔드 난이도 | 높음 (제안 알고리즘) | **낮음** (합성 잡만) | 높음 (슬롯 매칭 + 카탈로그) |
| 운영 비용 | 낮음 | 낮음 | **높음** (레시피를 계속 만들어야 함) |
| 최대 리스크 | 제안이 엉성하면 즉시 신뢰 상실 | 차별점 없음 — 평범한 편집 앱 | 매칭 오류 시 수정 비용이 크다 |

## 7. 추천

**P3(레시피)를 뼈대로 잡고, P2의 편집기를 무비 상세에 흡수하고, P1의 제안 카드는 나중에
레시피 탭 상단에 얹는다.** 세 방향은 배타적이지 않다 — 단계로 놓을 수 있다.

근거:

1. **콜드 스타트가 지금 가장 큰 리스크다.** 사용자도 데이터도 0인 상태에서 P1은 빈 홈을,
   P3는 “이걸 찍어오세요”를 보여준다.
2. **P3만 촬영을 만들어낸다.** 빈 슬롯 → 촬영 지시 → 스냅 증가 → 매칭 품질 상승. 다른
   두 방향에는 이 되먹임 고리가 없다.
3. **레시피 슬롯이 AI 합성의 명세가 된다.** 백엔드 입장에서 “알아서 잘 만들어줘”보다
   “5개 슬롯에 이 스냅들을 이 순서로”가 훨씬 구현 가능한 요구사항이다.
4. **실패해도 폴백이 있다.** 매칭이 틀리면 “직접 고르기”, 슬롯이 비면 “건너뛰기”.
   P1은 제안이 나쁘면 대안이 없다.

단계 제안:

| 단계 | 내용 | 이 방향에서 가져오는 것 |
| --- | --- | --- |
| v1 | 4탭 + 촬영, 스냅 그리드, 레시피 6종 고정, 자동 매칭, 합성 잡 | P3 |
| v1.1 | 무비 상세에 컷 순서/트림/스타일 편집기 | P2 |
| v1.2 | 레시피 탭 상단에 “오늘의 제안” 카드 | P1 |
| v1.3 | 프롬프트 → 커스텀 레시피 (자유 입력) | P3 확장 |

**단, P3를 고르면 레시피 카탈로그를 계속 운영해야 한다는 걸 감수해야 한다.** 이걸 감당할
사람이 없다면 P2로 시작하는 편이 정직하다 — 차별점은 약해지지만 운영 비용이 0에 가깝다.

## 8. 백엔드에 필요한 계약 (초안)

세 방향 모두 **합성 잡**은 동일하게 필요하다. 여기부터 시작하면 방향이 바뀌어도 버려지지 않는다.

```text
POST /snaps                  스냅 업로드 (video + 메타: 촬영시각, 길이, 위치, 해상도)
GET  /snaps?cursor=          내 스냅 목록

POST /movies                 { snapIds[] (≤10), order[], trims[], style, bgm, ratio }
                             → { movieId, jobId, status: "generating" }
GET  /movies/:id             → { status: draft|generating|ready|failed, renderedUrl?, error? }
PATCH /movies/:id            초안 수정 (순서/트림/스타일) — 재생성 없이 저장
POST /movies/:id/regenerate  같은 스냅 세트로 다시 합성 (seed/style 변경)
```

합성 잡에 반드시 필요한 옵션 하나: **사용자가 정한 순서와 트림을 그대로 지키는 모드.**
사용자가 컷을 옮겼는데 AI가 다시 정렬해 버리면 편집 기능 자체가 무의미해진다.

방향별 추가:

- **P1** — `GET /suggestions` : 스냅 메타(시각·위치·유사도)로 묶음 후보 N개 + 근거 문구.
- **P3** — 레시피 스키마를 **서버가 소유**해야 한다(앱 배포 없이 레시피 추가).
  `GET /recipes`, `POST /recipes/:id/match → 슬롯별 후보 스냅 + confidence`.
  매칭을 위한 스냅 장면 인덱싱(객체·장소·시간대) 파이프라인이 선행 조건.

알림도 하나 필요하다: **무비 완성 푸시.** 합성이 40초씩 걸리면 사용자는 앱을 나간다.
기존 FCM 인프라를 그대로 쓸 수 있다.

## 9. 아직 안 정한 것

- **공유/소셜을 넣을 것인가.** 지금은 “내보내기 + 외부 앱 공유”만 가정했다. 앱 안에
  피드가 생기면 탭 구조가 다시 바뀐다. (프로토타입 3종 모두 소셜 없음)
- **무비 길이 상한.** 스냅 10개 × 5초 = 최대 50초. 숏폼 기준으로는 적당하지만,
  트림으로 줄일지 목표 길이를 먼저 정할지는 미정.
- **스냅 보관 정책.** 원본을 서버에 올릴지, 기기에만 두고 합성 때만 업로드할지.
  용량·비용·계정 이전이 전부 여기에 걸린다.
- **기존 사용자 데이터.** 현재 롤/클립 데이터가 로컬에만 있으므로 마이그레이션 부담은
  낮지만, 이미 만든 롤을 무비로 변환할지 버릴지는 결정 필요.
