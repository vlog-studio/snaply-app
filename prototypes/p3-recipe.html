레시피 — 의도 우선형

가정: 사람들이 막히는 지점은 “무엇을 만들지”이지 “어떻게 만들지”가 아니다. 그래서 결과물의 모양(레시피)을 먼저 고르고, AI가 라이브러리에서 거기 맞는 스냅을 자동으로 채운다. 비는 장면이 있으면 “이 컷을 지금 찍어오세요”라고 시킨다 — 앱이 촬영을 지시한다.

탭 구성

레시피·스냅·● 촬영·무비·나

홈은 라이브러리도 제안 목록도 아니고 “만들 수 있는 것들의 카탈로그”다. 상단 프롬프트 한 줄로 원하는 걸 직접 적을 수도 있다.

무비를 만드는 두 경로

레시피 선택→AI 자동 매칭→빈 장면 채우기→생성
스냅→선택 (최대 10)→레시피 없이 바로 만들기

이 방향의 진짜 무기는 역방향 루프다. 라이브러리가 촬영을 만들어낸다 — “골목 컷이 없어요 → 지금 찍기”. 스냅 수집률이 구조적으로 올라간다.

강점 / 리스크

  • 결과물 품질이 예측 가능하다 — 레시피가 곧 품질 보증서.
  • 촬영 동기를 앱이 직접 만들어준다(빈 슬롯 → 촬영 지시).
  • 레시피는 콘텐츠다. 시즌·챌린지·브랜드 협업으로 계속 늘릴 수 있다.
  • 콜드 스타트가 가장 강하다 — 스냅 0개여도 “뭘 찍으면 되는지”가 보인다.
  • 자동 매칭이 틀리면 손보는 비용이 크다(신뢰 급락).
  • 레시피 카탈로그를 계속 운영해야 한다 — 콘텐츠 운영 비용.
  • 자유도가 낮게 느껴질 수 있다(“내 마음대로 못 만든다”).

백엔드에 필요한 것

  • 레시피 스키마 — 슬롯 정의(라벨·요구 조건·길이)를 서버가 관리. 클라이언트 배포 없이 추가 가능해야 한다.
  • 매칭 API — POST /recipes/:id/match → 슬롯별 후보 스냅 + confidence.
  • 매칭에 쓸 스냅 메타(장면 분류·객체·시각·위치) 인덱싱 파이프라인.
  • 합성 잡은 P1/P2와 동일.
